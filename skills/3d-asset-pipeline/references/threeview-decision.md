# 三视图生成方式：实测决策

日期：2026-10-02　测试对象：星见雅（Hoshimi Miyabi / 绝区零）
环境：本机 Linux + mihomo 代理 127.0.0.1:7897，MiniMax `image-01`，出图走 `POST /v1/image_generation`

## 结论（先说结果）

1. **用路线 A：一次出 turnaround sheet。** 路线 B（`subject_reference` 锁角色）**当前不可用**。
2. 但**不能无脑三等分裁**：模型有时画 3 个、有时 6 个、有时把中间朝向画错。
   所以必须**按实际人形区间裁** + **数不对就自动重试**。
3. 即便切对了，**朝向对不对仍要人眼/VLM 复核**，脚本保证不了。

## 路线 A：单次出图 + 按人形裁切 ✅ 采用

一次请求出「左正面 / 中侧面 / 右背面」三人并排图。

| 尝试 | 提示词 | 宽高比 | VLM 判读结果 | 脚本判定 |
|---|---|---|---|---|
| A-v1 | 笼统 "three orthographic views" | 21:9 | ❌ 正面+两个侧面，**没有背面**；图上带小字标注和签名 | — |
| A-v2 | 逐个指定朝向 + 压文字 | 21:9 | ✅ 正面/侧面/背面 | accept（3 段） |
| A-v2 | 同上 | **16:9** | ✅ 正面/侧面/背面，裁切块人物完整 | accept（3 段） |
| e2e-1 | 同上（脚本首次跑） | 16:9 | ❌ 3 个人形但**中间是正面不是侧面** | accept（切对了，朝向错） |
| e2e-2 | 同上 | 16:9 | ❌ **画了 6 个人形** | **reject**（检出 4 段 ≠ 3，自动重试） |
| e2e-3 | 同上 | 16:9 | ✅ 正面/侧面/背面，同一角色 | accept（3 段） |

**成功率约 3/5**。这就是为什么必须有自动重试和校验。

### 裁切：用 `detect_bands()`，不要三等分

按列算「有没有墨」→ 取连续墨段 → 合并小缝隙 → 过滤太窄的段。
段数 **必须正好 3** 才认，否则丢弃重试。

实测这比三等分更准：e2e-1 的三个人形实际落在
`(102,365) (538,776) (944,1153)`，而三等分是 `(0,426) (426,853) (853,1280)` ——
三等分会切掉人物的头和脚。

回归测试 `scripts/test_detect_bands.py` 用上面 4 张已知图锁住行为：
3 张好图必须 accept，6 人形那张必须 reject。

### 宽高比

- 16:9 → 1344×768，每块更高，人物完整。**默认用这个。**
- 21:9 → 1344×416，每块只有 416px 高，纵向不够。**别用。**

## 路线 B：`subject_reference` ❌ 不可用

| 传法 | 结果 |
|---|---|
| 裸 base64 | ❌ `status_code=1000 disallowed image url: localhost or private address not allowed` |
| `data:image/jpeg;base64,` | ❌ 同上 |
| 512px 缩图降体积 | ❌ 同上（与体积无关） |

> ⚠️ 推翻了「出图参考图 `subject_reference` ✅ 收 base64，不需要公网 URL（实测）」的旧结论。
> 接口现在把该字段当 URL 做 SSRF 校验，非公网一律拒。**要用参考图必须先传公网图床。**

`threeview.py` 因此支持 `--ref-url`（有公网 URL 时启用锁角色），本地图则走不通这条路。

## 连带影响：链路头一环暂时断

「输入图 → 三视图」这一步**暂时无法保持角色一致性**，只能走「文字描述 → 三视图」。
没有公网图床时的替代：用 VLM 读输入图拿到外观描述，再喂给 `--desc`——
一致性不如锁参考图，但链路能跑通。

## 视频首帧：必须 data URL；`1026 input new_sensitive` 是**会飘的**

- **裸 base64 被拒**：`status_code=2013 invalid params, first_frame_image: invalid image url`
- **`data:image/png;base64,` 可提交**（拿到 task_id）✅
- 两条首帧格式硬约束，`to_data_url()` 已自动处理：
  - 短边 ≥ **300px**，否则 `2013 ... minimum pixel on the short side of the image: 300px`
    （三视图裁出的侧面常常只有 130px 宽，必踩）
  - 长宽比在 **0.5~2**，否则 `2013 ... aspect ratio not between 0.5 and 2`

### ⚠️ `1026 input new_sensitive` 不是永久封禁

一开始星见雅的正面图、背面图、抠图正方图**全被拦**，一度判断成"要公网图床才走得通"。
**第二天复测，同一张 `miyabi_v2_front.png`、同一把 key，直接过了。**

对照实验（用来区分"通道坏了"还是"内容被禁"）：

| 样本 | 判定 | 说明 |
|---|---|---|
| `smoke_0.png`（红苹果） | **PASS** | 明确无害，走同一条 data URL 通道 → 通道没问题 |
| `miyabi_bust.png`（半身） | **PASS** | 角色半身图可以过 |
| `generic_anime.png`（非 IP 原创角色） | **PASS** | 动漫女性角色图不是普遍被禁 |
| `miyabi_v2_side.png`（侧面） | BLOCKED | 这次是 2013 尺寸/比例不合规，**不是**内容问题 |
| `miyabi_v2_front.png`（正面） | **PASS** | 前一天被拦，同条件复测就过了 |

所以结论是：**审核判决会漂，遇到就重试**。别一被拦就去折腾图床。

### 诊断技巧：审核判决出得很早

轮询状态机里，`Fail` + 1026 通常几十秒内就返回，而渲染要几分钟。
所以**轮询到 `Processing` 就说明已经过审**，可以不等渲染完。
`probe_moderation.py` 用这个技巧做鉴别实验，一个样本十几秒出结论。
