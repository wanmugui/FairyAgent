# Deep Research

## 用户可见输出守则

本节只约束**面向用户的自然语言阶段性回复**（assistant 文本中用户能看到的句子）。**不约束**最终成文中的 `<cite>` 引用标签和 `create_subtask` 的工具参数——这些该出现的地方按规范照常出现。

在用户可见的阶段性回复中：

- 禁止出现 `subtask` / `create_subtask` / `web_search` / `web_fetch` / `ask_user` / `finds` / `open_issues` / `section-evidence` / `slug` 等内部工具名、术语和字段名；用"子任务"、"网络搜索"、"网页抓取"、"关键发现"、"未确认项"、"章节大纲"等自然表达替代。
- 禁止中英术语混杂，全部按当前回复语言改写。

## 核心约束

- 先对齐需求，再开始调研。
- 主线程先拆“步骤”，再把每个步骤拆成多个 `create_subtask`。
- 每个 `subtask` 只负责一个细分、具体、边界清晰的任务。
- `subtask` 的主产物是执行结果，不是引用清单。
- `finds` 只承载后续正文会直接引用的关键发现。
- 最终报告的引用体系必须同时覆盖网页来源、用户上传文件与 `/mnt/data` 下本地文档 / 解析产物。
- Deep Research 不强制导出文件；研究收口后必须先判断交付形态，再开始最终成文。
- 当进入最终成文阶段时，按交付形态按需读取 `document-writing` skill，再开始写最终报告。

## 标准流程

### 1. 先检查需求是否明确

如果以下任一项会影响调研路径，就先调用 `ask_user`，不要直接开始搜集材料：

- 研究对象不明确
- 时间范围不明确
- 地域范围不明确
- 比较维度不明确
- 输出形式不明确
- 用户目标或验收标准不明确

### 2. 主线程先拆步骤

需求明确后，主线程先把任务拆成若干“可独立验收”的步骤。每个步骤必须写清楚：

- 目标
- 范围
- 预期产出
- 验收标准

不要把步骤写成“搜一下”“打开网页”“看资料”这种工具动作。

### 3. 每个步骤再拆成多个 `subtask`

进入具体步骤后，再把该步骤拆成多个子任务。每个 `subtask` 必须满足：

- 单一目标
- 明确输入
- 明确输出
- 不承担整篇报告
- 不替主线程做最终汇总

适合交给子任务的内容：

- 核实一个事实
- 研究一个子主题
- 比对一个维度
- 收集一组来源
- 提炼一个结论所需的证据

### 4. `subtask` 返回执行结果与关键发现

输出格式由工具定义（`<subtask_result>` XML 结构），五个子标签：

- `<original_task>` — 回显被委派的任务内容
- `<findings>` — 关键发现：具体事实、数字、引用、证据
- `<result>` — 最终结论/答案（唯一展示给用户的字段，面向用户语言）
- `<cite_files>` — 执行过程中引用、创建或修改的文件
- `<plan>` — 剩余工作、阻塞点、或给主线程的后续建议

注意
- `<result>` 是唯一展示给用户的字段，`<findings>` 是其事实支撑
- 来源标注使用 `<cite>` 标签融入 `<findings>` 文本，文件路径同时收入 `<cite_files>`，便于主线程统一整理引用体系

### 6. 研究收口后先判断交付形态，再统一成文

当所有研究步骤都已完成，并且关键风险已处理后，主线程才进入最终汇总。

先按以下规则判断交付形态：

- 用户明确要求导出文件，或任务的唯一可用交付物必须是文件时，走“文件成文流程”
- 其他情况，走“直接回复流程”
- 不要因为任务触发了 Deep Research、报告型任务、或内容篇幅较长，就自动写入 `/mnt/data/result` 或强制生成文件

如果走“文件成文流程”，读取并执行 `document-writing` 的文件成文流程。

如果走“直接回复流程”，可以读取 `document-writing` 中的章节覆盖与证据覆盖规则，但不强制写 draft 文件、不强制生成 section index、不强制逐节 reflection。

最终成文要求：

- 必须吸收所有步骤、所有已完成 `subtask` 的执行结果，不能只保留少量高层结论
- 保留所有需要呈现给用户的关键发现，并默认尽量保留分析内容与中间结论
- 如果多个 `subtask` 覆盖不同维度，最终文章必须把这些维度分别写出来，不要为了简短而把独特结果合并抹平
- 如果某个 `subtask` 已经整理出表格、矩阵、时间线、状态路径或分厂商 / 分地区 / 分维度比较，最终文章必须保留等价结构；可以重写表达，但不能把结构化结果压成几句泛化结论
- 每个已完成 `subtask` 至少要以一种用户可见方式留下痕迹：正文段落、表格行、独立小节、风险项、附录条目，四者至少其一
- 如果正文篇幅压力过大，优先把高密度材料写进“附录 / 补充材料 / 对比矩阵”，而不是直接删除
- `open_issues` 里只要存在与用户决策相关的缺口、冲突或未确认项，就要进入最终文章的“风险 / 未确认项”部分，而不是在总报告里消失
- 只有在内容明显重复、偏离用户目标或证据不足时，才允许压缩或删减；默认应偏向“保留更多结果”而不是“写得更短”
- 最终交付应完整吸收研究材料，而不是把大部分 `result` 缩成几条摘要。
- 统一整理全局 `<cite>`
- 输出完整文章，而不是拼接子任务原文

## 输出要求

### 最终文章结构

```text
1. 背景与目标
2. 分步骤结论
3. 综合分析
4. 风险 / 未确认项
5. 对比矩阵 / 附录（必要时）
```

额外要求：

- 正文中直接保留 inline `<cite>`
- 用户上传文件、本地文档及网页来源共用同一套引用编号；文件来源的 `title` 默认写文件名
- 最终交付必须是完整文章，不是过程记录；交付介质按第 6 步判断
- 若某个 `subtask` 的结果主要以表格、矩阵、清单或时间线形式最清晰，允许直接在正文或附录里保留 Markdown 结构，不必强行改写成纯段落

## 工具路由

- `ask_user`：只在需求不明确且会影响执行路径时使用
- `create_subtask`：用于执行步骤内的细分任务
- `document-writing`：用于最终报告进入成文阶段后的交付形态判断、直接回复成文或文件成文
- 其他材料获取工具（如 `web_search`、`web_fetch`、`document_parser`、`read_file`）只服务于步骤执行，不替代这套主流程
