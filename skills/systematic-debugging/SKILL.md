# Systematic Debugging

## 概述

**核心原则：** 在尝试任何修复之前，必须找到根因。仅处理症状即是失败。

**违反此过程的字面即是违反调试的精神。**

## 铁律

```
无根因调查，不得修复
```

如果你尚未完成阶段 1，你不能提出修复。

## 何时使用

用于任何技术问题：

- 测试失败
- 生产中的 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**特别是在以下情况下使用：**
- 在时间压力下（紧急情况下容易猜测）
- "只是一个快速修复"看起来显而易见
- 你已尝试了多个修复
- 先前的修复无效
- 你没有完全理解该问题

**不要在以下情况下跳过：**
- 问题看起来简单（简单的 bug 也有根因）
- 你很匆忙（匆忙保证返工）
- 经理希望立即修复（系统化比胡乱尝试更快）

## 四个阶段

你必须在进入下一阶段之前完成每个阶段。

### 阶段 1：根因调查

**在任何修复尝试之前：**

1. **仔细阅读错误消息**
   - 不要跳过错误或警告
   - 它们通常包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 记下行号、文件路径、错误码

2. **一致地复现**
   - 你能可靠地触发它吗？
   - 确切的步骤是什么？
   - 是否每次都发生？
   - 如果不可复现 → 收集更多数据，不要猜测

3. **检查最近的变更**
   - 什么变化可能引起此问题？
   - Git diff、近期提交
   - 新的依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统具有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复之前，添加诊断探针：**
   ```
   对于每个组件边界：
     - 记录进入组件的数据
     - 记录退出组件的数据
     - 验证环境/配置传播
     - 检查每一层的状态

   运行一次以收集证据显示在哪里中断
   然后分析证据以识别失败的组件
   然后调查该特定组件
   ```

   **示例（多层系统）：**
   ```bash
   # 第 1 层：工作流
   echo "=== 工作流中可用的 secrets: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第 2 层：构建脚本
   echo "=== 构建脚本中的环境变量: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 第 3 层：签名脚本
   echo "=== Keychain 状态: ==="
   security list-keychains
   security find-identity -v

   # 第 4 层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示了：** 哪一层失败（secrets → 工作流 ✓，工作流 → 构建 ✗）

5. **追踪数据流**

   **当错误深藏在调用栈中时：**

   有关完整的反向追踪技术，请参阅此目录中的 `root-cause-tracing.md`。

   **快速版本：**
   - 错误值源自何处？
   - 谁使用错误值调用了此？
   - 一直向上追踪直到找到源头
   - 在源头修复，而不是症状处

### 阶段 2：模式分析

**在修复之前找到模式：**

1. **找到工作中的示例**
   - 在同一代码库中定位类似的工作代码
   - 类似的、工作的内容与破碎的内容有什么关系？

2. **对照参考**
   - 如果实现某个模式，请完整阅读参考实现
   - 不要略读 - 逐行阅读
   - 在应用前完全理解模式

3. **识别差异**
   - 工作与破碎之间的差异是什么？
   - 列出每个差异，无论多小
   - 不要假设"那无关紧要"

4. **理解依赖**
   - 这还需要哪些其他组件？
   - 哪些设置、配置、环境？
   - 它做出哪些假设？

### 阶段 3：假设与测试

**科学方法：**

1. **形成单一假设**
   - 明确陈述："我认为 X 是根因，因为 Y"
   - 写下来
   - 要具体，不要模糊

2. **最小化测试**
   - 对假设进行尽可能最小的更改
   - 一次一个变量
   - 不要一次修复多个

3. **在继续之前验证**
   - 起作用了吗？是 → 阶段 4
   - 没起作用？形成新假设
   - 不要在其上叠加更多修复

4. **当你不了解时**
   - 说"我不了解 X"
   - 不要假装知道
   - 请求帮助
   - 研究更多

### 阶段 4：实施

**修复根因，而非症状：**

1. **创建失败的测试用例**
   - 最简单的复现
   - 如可能自动化测试
   - 若无框架则一次性测试脚本
   - 必须在修复之前
   - 使用 `superpowers:test-driven-development` 技能编写合适的失败测试

2. **实施单一修复**
   - 解决已识别的根因
   - 一次一个更改
   - 没有"既然我都到这里了"的改进
   - 没有捆绑重构

3. **验证修复**
   - 测试现在通过吗？
   - 没有其他测试被破坏？
   - 问题实际解决了吗？
   - 在宣称成功之前使用 `superpowers:verification-before-completion` 技能

4. **如果修复不起作用**
   - 停止
   - 计数：你已尝试了多少修复？
   - 若 < 3：返回阶段 1，使用新信息重新分析
   - **若 ≥ 3：停止并质疑架构（见下面的步骤 5）**
   - 不要在没有架构讨论的情况下尝试第 4 个修复

5. **如果 3+ 修复失败：质疑架构**

   **指示架构问题的模式：**
   - 每个修复在不同地方揭示新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实施
   - 每个修复在其他地方产生新症状

   **停下来质疑基本原理：**
   - 这个模式从根本上合理吗？
   - 我们是否"仅凭惯性坚持"？
   - 应该重构架构还是继续修复症状？

   **在尝试更多修复之前与你的伙伴讨论**

   这不是失败的假设——这是错误的架构。

## 红旗 - 停止并遵循流程

如果你发现自己这样想：
- "暂时快速修复，稍后调查"
- "只需尝试更改 X 看看是否起作用"
- "添加多个更改，运行测试"
- "跳过测试，我会手动验证"
- "可能是 X，让我修复它"
- "我没有完全理解，但这也许有效"
- "模式说 X 但我会不同地适配它"
- "这里是主要问题：[未调查列出修复]"
- 在追踪数据流之前提出解决方案
- **"再尝试一次修复"（已经尝试过 2+ 次）**
- **每个修复在不同地方揭示新问题**

**所有这些都意味着：停止。返回阶段 1。**

**如果 3+ 修复失败：** 质疑架构（见阶段 4.5）

## 你的伙伴表示你做错了的信号

**注意这些重定向：**
- "那没有发生吗？" - 你假设了未验证的内容
- "它会向我们展示...吗？" - 你本应添加证据收集
- "停止猜测" - 你在不理解的情况下提出修复
- "Ultra-think this" - 质疑基本原理，而不仅仅是症状
- "我们卡住了吗？"（沮丧的）- 你的方法不起作用

**当你看到这些：** 停止。返回阶段 1。

## 常见合理化

| 借口 | 现实 |
|--------|---------|
| "问题简单，不需要流程" | 简单问题也有根因。流程对简单的 bug 很快。 |
| "紧急情况，没有流程时间" | 系统化调试比猜测-检查胡乱尝试更快。 |
| "先试这个，然后调查" | 第一次修复设定了模式。从一开始就做对。 |
| "确认修复有效后我会写测试" | 未测试的修复不持久。先测试证明它。 |
| "多个修复一起省时" | 无法隔离起作用的内容。引发新的 bug。 |
| "参考太长，我会适配模式" | 部分理解保证 bug。完整阅读。 |
| "我看到问题了，让我修复它" | 看到症状 ≠ 理解根因。 |
| "再尝试一次修复"（2+ 失败后） | 3+ 失败 = 架构问题。质疑模式，不要再修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 读取错误，复现，检查变更，收集证据 | 了解内容与原因 |
| **2. 模式** | 找到工作中的示例，比较 | 识别差异 |
| **3. 假设** | 形成理论，最小化测试 | 确认或新假设 |
| **4. 实施** | 创建测试，修复，验证 | Bug 已解决，测试通过 |

## 当流程揭示"无根因"时

如果系统化调查揭示问题确实是环境性、时序依赖或外部的：

1. 你已完成流程
2. 记录你调查的内容
3. 实施适当的处理（重试、超时、错误消息）
4. 添加监控/日志记录以便将来调查

**但是：** 95% 的"无根因"案例是调查不完整。
